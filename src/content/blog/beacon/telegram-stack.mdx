Sending the same poll to three Telegram chats creates three polls, each with its own ID. A committee wants one answer to its question, but the bot receives votes attached to those separate IDs. Beacon needs to preserve that relationship before it can produce a useful total.

This chapter follows the [repository version](https://github.com/Ducksss/beacon/tree/cfaabc3612e15506dfa7f89d6ab99efe12b5d91f), which includes changes after the hackathon. The app uses Next.js route handlers to call the Telegram Bot API and a Supabase database to retain the message and poll mappings.

## The IDs that join the system together

For an announcement, Beacon creates a broadcast row, sends a message to each target chat and stores the returned message ID alongside that chat's ID. Corrections can then address the right copy.

A poll adds a master question, its ordered options and a mapping for every Telegram poll created by the send:

```text wrap=false
broadcasts
  |
  +--> polls: one master question
         |
         +--> poll_options: option 0, option 1, ...
         |
         +--> telegram_polls
                poll A --> master question + chat A
                poll B --> master question + chat B
                poll C --> master question + chat C
                   |
                   +--> votes: Telegram poll + user + option index
```

The [schema](https://github.com/Ducksss/beacon/blob/cfaabc3612e15506dfa7f89d6ab99efe12b5d91f/web/supabase/schema.sql) stores option indexes because Telegram answers identify selected options by their position. Keeping the same order in every chat lets the dashboard combine option 0 with option 0, rather than trying to match answers by their wording.

## A changed answer replaces the old one

Beacon sends single-choice, non-anonymous polls. Telegram provides individual [poll-answer updates](https://core.telegram.org/bots/api#update) for non-anonymous polls sent by the bot, and an update represents a user's changed selection rather than an instruction to increment a permanent counter.

The [update handler](https://github.com/Ducksss/beacon/blob/cfaabc3612e15506dfa7f89d6ab99efe12b5d91f/web/src/lib/telegram-updates.ts) deletes the existing vote for that Telegram poll and user, then inserts the newly selected option. If the answer contains no selected option, it leaves the old vote deleted. A database uniqueness constraint on `(telegram_poll_id, user_id)` also prevents multiple rows for the same person in the same poll copy.

For example, changing from option 0 to option 1 should leave one row for option 1, while withdrawing the answer should leave none. Counting incoming events would get both cases wrong because an event is not necessarily an additional voter.

## Combined votes are not unique people

The dashboard looks up all Telegram poll IDs belonging to a master question, then counts the stored answers by option index. This produces a combined tally across the chat copies.

The uniqueness constraint applies to each Telegram poll, though, rather than to the master question. Someone in two house chats can answer both copies and contribute two votes to the combined result. The tally is therefore a count of recorded answers, not necessarily a count of distinct people answering that question.

Non-anonymous polls also mean the database holds Telegram user IDs. That is a real trade-off in this implementation, even when the dashboard presents only aggregate results.

## Receiving answers has its own failure cases

The repository has two paths for incoming updates. A configured webhook forwards them to a route handler. Without a webhook, a dashboard request can fetch pending updates through `getUpdates`. Telegram treats [webhooks and polling](https://core.telegram.org/bots/api#getting-updates) as alternative ways to receive updates, so the fallback first checks whether a webhook is set.

Neither path makes the prototype a reliable vote ledger by itself. The vote handler performs deletion and insertion as separate database operations and does not check their returned errors. If replacement fails after deletion, the old answer is gone without a new one being stored.

The [webhook route](https://github.com/Ducksss/beacon/blob/cfaabc3612e15506dfa7f89d6ab99efe12b5d91f/web/src/app/api/webhook/telegram/route.ts) also returns HTTP 200 when its error handler runs. Telegram [retries unsuccessful webhook requests](https://core.telegram.org/bots/api#setwebhook), so acknowledging an error removes that opportunity to receive the update again. A dashboard can combine only the answers that made it into the database, and these failure cases can leave a tally incomplete even when the chart loads normally.
