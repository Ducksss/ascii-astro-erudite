The real-time messaging work was a separate prototype, outside MetaLearner's production scope. The [repo is named socketio-chat](https://github.com/Ducksss/socketio-chat), but its implementation uses FastAPI WebSocket endpoints with PostgreSQL and Redis pub/sub.

Its interesting problem appears when there is more than one backend process. A WebSocket belongs to the process that accepted its connection, so a message arriving at process A cannot reach a browser connected to process B through A's local connection list alone.

## Storing the message and notifying the listeners

The prototype separates those two jobs. PostgreSQL holds messages and unread records, while Redis carries a notification between backend processes.

```text wrap=false
Sender --> Process A --> PostgreSQL: message + unread records
                |
                v
             Redis: group notification
                |
        +-------+-------+
        v               v
    Process A       Process B --> read unread records
                                  --> connected browser
```

The [send and receive handlers](https://github.com/Ducksss/socketio-chat/blob/21d477ea2b690396a59af6565f39f9e065df51e7/backend/chat/views/websocket.py) make that flow visible:

1. The sender's message is stored in PostgreSQL.
2. An unread record is created for each member of the group.
3. The backend publishes a Redis event containing the group ID.
4. Each subscribed backend wakes its local listeners for that group.
5. Those listeners read unread records from PostgreSQL and send the messages through their own WebSockets.

The group ID tells a backend which listeners to wake. Redis does not need to carry the complete message because the receiving process can read it from the database. This is fan-out: one notification reaches several processes, and each process serves the connections it owns.

Edit and delete events take a different path. Their Redis payload contains the change details, which the [event manager](https://github.com/Ducksss/socketio-chat/blob/21d477ea2b690396a59af6565f39f9e065df51e7/backend/chat/realtime.py) sends directly to local listeners.

## A notification is not a delivery guarantee

[Redis pub/sub has at-most-once delivery](https://redis.io/docs/latest/develop/pubsub/#delivery-semantics). A subscriber that misses an event cannot ask pub/sub to replay it later.

In this prototype, an unread message remains in PostgreSQL until the receive handler sends it and removes the unread record. The handler checks unread records when a listener connects, then waits for notifications when there is nothing pending. Reading that flow shows a limit: a missed notification can leave an already connected listener waiting even though an unread record exists. Reconnecting triggers another database check, but pub/sub itself does not repair the missed signal.

That distinction is useful when reading the architecture. Adding Redis lets a process notify peers, while reliable recovery requires its own design. This repo is a reference implementation of the message path, rather than evidence of a measured throughput or production delivery guarantee.
