The MetaLearner Figma work explored how chat, KPIs, graphs and alerts could fit together in the frontend. It included a review of the existing interface, responsive layouts, industry references and a developing design system.

These were design explorations alongside the frontend work I implemented. The [Figma file](https://www.figma.com/design/uoDY5aY1Nk7Qflo3dSn0qn/MetaLearner_Frontend?node-id=2191-3428) is the reference for the proposed direction.

## Moving from mobile exploration to the desktop workflow

I initially explored mobile layouts. Team review then clarified that desktop was the primary operating surface, so the direction moved towards desktop layouts and a more central chat workflow. The [handoff](https://metalearner-internship-logs.vercel.app/) records that change.

This changes the design problem. On a small screen, the interface has to decide what to show first and what to move elsewhere. On a desktop, there is room to show a conversation beside data, but the extra space still has to be divided between competing tasks.

Making chat prominent is one such choice. It gives the user a direct place to ask for a comparison or narrow a question, while keeping data beside the conversation gives them something to refer to. At the same time, a persistent chat panel takes width away from charts and tables. More space for one does not automatically make the whole screen easier to use.

That is why the move towards desktop was more than enlarging a mobile layout. It put the relationship between conversation and data at the centre of the exploration.

## Decisions within the dashboard

The layouts explored KPI cards, alert states, overlays and category-based filtering. Each carries a different design question:

| Element          | Question to resolve                                                       |
| ---------------- | ------------------------------------------------------------------------- |
| KPI cards        | Which numbers need to be visible before the user asks for detail?         |
| Alerts           | What needs attention, and how does that differ from ordinary status?      |
| Overlays         | Which details can appear temporarily without taking over the main view?   |
| Category filters | Which grouping helps the user narrow the information on screen?           |
| Chat             | What data should remain visible while the user asks a follow-up question? |

Those questions help make a review concrete. “Improve the hierarchy” becomes a decision about whether an alert, a KPI or the conversation should draw attention first. “Make it responsive” becomes a decision about which of those elements can move or collapse when there is less room.

## A shared vocabulary for the interface

The file explored a ShadCN-based direction and collected components, typography, colours, primitives and icons. Shared choices give screens a common vocabulary, but a component library cannot decide what information deserves prominence.

An alert colour, for example, has to mean something consistent across the interface. If it is also used casually for decoration, it becomes harder to distinguish a warning from an ordinary card. Typography has a similar job: a reader should be able to tell a section heading, a metric and its supporting label apart without learning a new treatment on each screen.

The design work gave the team a place to discuss those decisions before translating them into components. The desktop shift is the clearest example of review changing the direction, because it changed what the layouts were organised around.
