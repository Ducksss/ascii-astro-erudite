> Updated 3 October 2026: the project is now called Payload Components. I have updated this article to reflect the shipped registry and CLI.

The idea grew out of repeated client website work. I contributed to design direction and development on collaborative projects for [Genium](https://genium.sg/) and [Octilyon](https://octilyon.com/), working alongside other designers and developers. Across projects, familiar section patterns kept returning: heroes, feature grids, FAQs and testimonials.

With Payload, building the section was only part of the job. I still had to connect its fields, frontend renderer and generated types to the host project. Recreating that setup took time away from the client's actual problem. [Payload Components](https://www.payload-components.xyz/) is my attempt to make that repeated work reusable.

## The repeated pain was not the blocks themselves

A block in a Payload v3 and Next.js project needs several pieces to agree:

- a typed block config defining its editor fields
- a frontend component rendering that content
- registration in the Pages collection's layout field
- a matching entry in `RenderBlocks`
- regenerated Payload types and the admin import map

Copying the component files leaves the rest of that work to the developer. When teams repeat the same setup across projects, a missed registration or stale generated file can leave a block unavailable in the editor or absent from the page.

I wanted the source and the installation instructions to travel together.

## Why I built Payload Components

Payload Components is an MIT, community-first registry and CLI for typed Payload CMS blocks. I maintain the project, including releases, issue triage and reviews. The source, installer and documentation are open, and contributions help decide what the catalog needs next.

Each block ships with an install contract describing its files, dependencies, Payload wiring and generation tasks. The CLI applies that contract in a supported project and leaves the result as a reviewable git diff. Developers keep the installed source in their own repository and can adapt it to their site.

## What it does

From the root of a supported Payload v3 and Next.js project, I can check the setup, preview an install and add a block:

```sh
npx payload-components doctor
npx payload-components add hero-basic --dry-run
npx payload-components add hero-basic
```

The install copies the source, installs missing dependencies, registers the block in Pages, maps its renderer in `RenderBlocks`, and runs `generate:types` and `generate:importmap`. It records the result in `.payload-components/state.json` so a repeated install can check what is already present without duplicating the wiring.

A bare `create-payload-app` project can establish the starter files with `npx payload-components init --scaffold`. That is an explicit setup step. Follow its registration guidance and run `doctor` before adding blocks.

The project also supports checking and maintaining recorded installs:

```sh
npx payload-components list
npx payload-components diff
npx payload-components update
```

`diff` reports source and wiring drift. `update` checks the recorded source before replacing files and refuses to overwrite local edits without an explicit override. Installation and maintenance are part of the same workflow.

## Who it is really for

Agencies and freelancers were the starting point because client websites made the repetition visible to me. The same problem applies to any team building content-managed sites with supported Payload project shapes.

The catalog includes families of website sections, with structural variants chosen by name. A team can pick the block it needs, inspect its fields and source, then install it into a project it already owns. The [component catalog](https://www.payload-components.xyz/components) is the current inventory.

## Payload-native integration

Shipping this taught me that developer experience is a systems problem. The component, installation, types, examples, error messages and documentation all need to agree.

The installer has to work with code I do not control. That means checking the host project before changing it, preserving local work, and testing the integration path. A block that looks right in a preview still needs to compile and render after installation in a real Payload project.

Those checks are where I spend much of the maintenance effort. They make the source easier to reuse without asking every developer to rediscover the same setup.

## What I do not want this to become

I want to keep the scope clear: useful, documented blocks for Payload v3 and Next.js, with an installer that respects the host repository.

The project is community-first. Its MIT source is available to use and contribute to, and the catalog grows through real installs, bug reports and pull requests. That is the kind of project I wanted when I kept rebuilding the same integration work for clients.
