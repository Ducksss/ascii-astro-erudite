On client websites, a familiar section could still take an unfamiliar amount of setup. I would have a hero or FAQ component ready, but it could not appear in Payload's editor until its configuration was registered. Even then, the frontend needed to know which component should render it, and the generated types needed to catch up.

I kept meeting that repetition while contributing to design and development on collaborative projects for [Genium](https://genium.sg/) and [Octilyon](https://octilyon.com/). The sites had different needs, but the route from “we need this section” to a working content-managed page was often the same.

[Payload Components](https://www.payload-components.xyz/) grew out of that work. It is an MIT registry and CLI that install the source for a block together with the wiring that makes it usable in a supported Payload v3 and Next.js project.

## A block has several places to exist

Consider a basic hero. The editor needs fields for its content, while the frontend needs a component that knows how to display that content. Those two files are only part of the path:

```text wrap=false
Block configuration
  | defines the fields an editor can fill in
  v
Pages collection's layout field
  | makes the block available in the admin
  v
Saved page content
  | carries a blockType and field values
  v
RenderBlocks mapping
  | selects the matching frontend component
  v
Rendered page

Generated types and the admin import map
must agree with the configuration alongside this path.
```

Copying a JSX file does not establish those connections. A missing collection registration means the editor cannot select the block. A missing renderer mapping means the frontend does not know what to do with the saved content. A stale generated file can leave the code and the configuration describing different versions of the same thing.

I wanted the installation instructions to travel with the source, because the connections were the part I kept having to reconstruct.

## What the installer changes

Each block has an install contract describing its files, dependencies, wiring fragments and generation tasks. For a supported project, I can inspect that plan before applying it:

```sh
npx payload-components doctor
npx payload-components add hero-basic --dry-run
npx payload-components add hero-basic
```

`doctor` checks the project shape and the files and scripts the install needs. The dry run shows the planned changes without copying files, installing dependencies or running generation commands. For `hero-basic`, the plan includes the block source, its registration in the Pages collection, its entry in `RenderBlocks`, and the generation tasks.

The real install applies that plan and runs `generate:types` and `generate:importmap`. The result stays in the host repository as source that the developer can read and change, rather than being hidden behind a hosted rendering service.

This depends on recognising the project. The CLI does not promise to understand every custom Payload layout. A bare `create-payload-app` project can use `npx payload-components init --scaffold` to establish the starter files, but that is a separate setup step with registration guidance to follow. The [installation guide](https://www.payload-components.xyz/docs/installation) describes the supported route.

## The second install matters as much as the first

A successful first run is only the beginning. Running the same command again should not add the same block registration twice, and updating a block should not quietly erase a client's changes.

The CLI records successful installs in `.payload-components/state.json`. That gives later commands a baseline for checking source and wiring rather than guessing from filenames alone:

```sh
npx payload-components list
npx payload-components diff
npx payload-components update
```

`diff` reports version, file and wiring drift. `update` compares the installed files with the source hashes recorded at the previous successful install. If I have edited a component locally, it skips that component and reports the conflict unless I explicitly override the protection.

That is a useful boundary for a source-copying tool. Once a file belongs to a project, it can contain work the registry has never seen. Having a newer registry version does not make that local work disposable.

## The preview is only one part of the component

The visible section is the easy part to demonstrate. The less visible questions take more maintenance: does it install in the supported starter, do its fields match what the renderer expects, does regeneration succeed, and does a repeated install converge on the same wiring?

Those questions are why the installer is part of the project rather than a footnote in the documentation. A component gallery can show the section I want. An install contract has to explain how that section joins the code I already have.

The [catalog](https://www.payload-components.xyz/components) shows the current blocks. The [registry and CLI source](https://github.com/Ducksss/payload-components) show how they are packaged and installed. Both are open under MIT, so the useful place to start is one block in a project you can inspect, followed by the diff it leaves behind.
